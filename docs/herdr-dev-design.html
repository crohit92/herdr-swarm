Design document · herdr-dev · 26 November 2026 · Status: draft for review

herdr-dev: design document

A Claude mod that works through your assigned Azure Boards items one at a time. Each item gets its own git worktree, a Claude agent in a Herdr pane, a pull request into main, and a Done status on the board.

Nothing is built yet. This document describes what will be built. Each decision is marked confirm or change where it is a default I chose. Tell me what to change and I will update this document before building.

1. Purpose and scope

You assign work to yourself on Azure Boards. herdr-dev picks it up on a timer, does it with an agent, and returns it to you as a pull request marked Done on the board. You review and merge the pull request yourself.

In scope

  • A /herdr-dev mod with three commands: start, stop, status.
  • A timer that runs one iteration per interval, read from the target project's .env.
  • Reading your assigned items, claiming one at a time, and running one agent at a time.
  • Per-item worktrees, branches, pushes, pull requests into the base branch, and Azure state changes.
  • Reporting conflicts and mismatches to you in a pane and with toasts. Deciding what to do about them is up to you.
  • Four Herdr plugin actions that do the outward steps (Azure writes, git push, pull request).

Out of scope

  • Merging pull requests. A person merges.
  • Work items not assigned to you, and items in other projects.
  • Editing any Azure field other than the state.
  • Running more than one item at a time, or more than one agent at a time.
  • Running while no Claude session is open. The loop lives in a session (see section 4).

2. Glossary and states

A flag lives from claiming to done. done flags stay as a record. Every other status is in progress and blocks the queue.

Why the mod and the actions talk through files

The mod and the actions are separate processes. Each action runs with Herdr's environment, including HERDR_PLUGIN_STATE_DIR, so an action does not need the mod to pass it anything. The mod has to pass one thing: the work item id, which an action cannot otherwise know. herdr plugin action invoke accepts no arguments, so that id goes through a small request file. The design keeps the channels as small as possible.

  • The actions write every state file that describes work: the fetched list and the flags. The mod reads them.
  • The mod writes almost nothing the actions need. The one exception is a small request file for an action that acts on one item: requests/<action>.json, containing { "workItemId": 12 }. The action deletes it after reading.
  • Action outcomes come from the plugin log, not from files. Invoking an action returns at once. The mod records the log_id it was given, then checks herdr plugin log list on later ticks until that run is no longer running. The exit code and stdout of that run are the outcome. A flag moved to archive/ still records a failure's reason for later reading.
  • The agent is different. It writes results/wi-<id>.json, and the mod reads it. This file is how the agent reports back.

The mod starts from a default state directory: $HERDR_DEV_STATE_DIR if set, otherwise ${XDG_STATE_HOME:-~/.local/state}/herdr/plugins/dev.automation. That path is observed on this machine, but Herdr does not document it. The fetch action prints the real HERDR_PLUGIN_STATE_DIR, and start compares the two (section 3, state directory).

4. Architecture

The loop runs in a Claude session. The mod's timer drives it, and the Herdr actions do the outward work. The agent runs in a pane that Herdr manages.

5. Commands

/herdr-dev start

  1. Resolve the target project (git root of the current folder) and read its .env (section 6). Stop with an error if anything is missing or invalid.
  2. If the loop is already running, say so and change nothing.
  3. Write active-project.json with the repo root and the settings, so actions never depend on the focused workspace.
  4. Set loop.json to running and arm the timer with $.clock.every.
  5. Run the first iteration now, not after one full interval.
  6. Confirm in one toast: "herdr-dev running every N seconds for <project>".

/herdr-dev stop

  • Cancel the timer and set loop.json to stopped.
  • Does not stop running agents and does not change flags or Azure state. Work in progress stays where it is.
  • Shows what is still running, so you can decide what to do with it.

/herdr-dev status

Shows, without changing anything:

  • Whether the loop is running, its interval, the last tick and its outcome, and the next tick.
  • The current item, its flag status, its agent, and how long it has been running.
  • The queue in priority order, with each item's Azure state.
  • Every open conflict and mismatch (section 9).

Behaviour across restarts

The loop lives in a Claude session. If the session closes, the timer stops, but agents and their panes keep running. When a session starts again and loop.json says running, the mod re-arms the timer and the next tick judges the state on disk. Nothing is assumed from memory, so a restart is safe.

7. State directory

Everything the loop knows is in this directory, so the loop can resume after a restart. Each file has one main writer.

<state dir>/
  active-project.json        settings and repo root           writer: mod (start)
  loop.json                  running flag, last tick          writer: mod
  work-items.json            fetched items, fetchedAt         writer: fetch action
  flags/wi-<id>.json          the lock and status              writer: mod (claiming), actions
  agents/wi-<id>.json         the agent that works an item     writer: mod
  results/wi-<id>.json        the agent's own report          writer: agent

  archive/wi-<id>-<ts>.json  flags that were ended, with reason  writer: actions, mod

8. One iteration

Each tick runs these guards in order. The first guard that stops the tick ends it, and the tick records one line of outcome in loop.json and shows it in status.

  1. Loop running? If not, stop. This is the only guard that is silent.
  2. Refresh the queue. Invoke dev-fetch-work-items and wait for its run in the plugin log. While it is running, stop this tick. If the run fails, report its stdout and stop. Do not judge flags against stale data.
  3. Any To Do items? If none, the tick is skipped. This is the no-open-items rule.
  4. Judge in-progress flags. For each flag in claiming, doing or finishing, check its agent (section 9). Hanging flags are reset or finished; a blocked or failed agent is reported. If any flag still blocks, stop here.
  5. Check for mismatches. Compare flags with Azure and the fetched items (section 9). Report them. Mismatches never stop the tick by themselves, but a mismatch on the item about to start does.
  6. Pick the top item. Lowest priority number among the To Do items, then lowest id.
  7. Does a flag already exist for it? If so, report it as a conflict and stop. Do not look at lower-priority items.
  8. Claim. Write flags/wi-<id>.json with status claiming. Write requests/claim.json, then invoke dev-claim-work-item (section 10).
  9. Wait for the claim. On later ticks, check the plugin log for the claim run's log_id. While it is running, stop the tick. When it has finished with exit code 0 and the flag is doing, continue. Otherwise report the run's stdout and the archived reason, and stop.
  10. Start the agent. Split a pane from the current tab, trust the worktree, start a Claude agent named wi-<id> there with bypassed permissions, and send the prompt (section 11). Write agents/wi-<id>.json.
  11. Done? On a later tick, if the agent is idle or done and results/wi-<id>.json exists with "status": "success", invoke dev-finish-work-item (section 10). The flag moves to finishing, then done.
  12. Close the finished pane. After the flag is done, close the item's pane and record the tick.

The loop never starts two items at once. Steps 4 and 7 both check for any in-progress flag, so the rule holds even if a previous run crashed.

9. Flags, hanging work, mismatches

Flag lifecycle

(no flag)→ claiming→ doing→ finishing→ done
  • claiming: the mod has written it, and the claim action is running. Azure is being moved to Doing.
  • doing: Azure is Doing, the worktree and branch exist, and an agent is working. Set by the claim action on success.
  • finishing: the agent succeeded, and the finish action is pushing, opening the pull request and setting Done.
  • done: Azure is Done and the pull request exists. Kept as a record.

Hanging work

A flag is hanging only when it is in progress and no live agent is working on it. If the agent is known and working, the flag is in progress, not hanging, however long the work takes. Hanging work is reset without asking you, as you decided.

FlagConditionAction
claimingStill claiming after 5 minutesArchive the flag, set Azure back to To Do, and retry the item on the next tick. Counts as an attempt.
doingThe agent record is missing, or herdr agent get no longer finds the agentClose its pane if one remains, archive the flag, set Azure to To Do, and count an attempt. The worktree and branch are kept, and the next prompt says it is a resumed attempt.
doingThe agent is idle or done, sawWorking is true, and there is no result fileThe same as above. The agent stopped without reporting.
doingThe agent is blockedReport only. Do not reset.
doingThe agent wrote "status": "failed"Report only. The flag blocks the queue until you decide.
doingAgent just started: not yet sawWorking and under 2 minutes oldWait. Not hanging yet.
finishingStill finishing after 10 minutesRun dev-finish-work-item again. It is idempotent: the push is repeatable, and an existing pull request is found before one is created. Not reset to To Do.

The time limits in the claiming and finishing rows apply to the actions, which have no agent. They never apply to a doing flag whose agent is known and working.

Retry cap. Each reset counts as an attempt, stored in the flag. At 3 attempts (HERDR_DEV_MAX_ATTEMPTS), the mod stops resetting the item and reports it as a conflict for you to decide. This protects you from an agent that never writes its result file, which would otherwise be retried indefinitely.

Mismatches (report only)

The mod never fixes a mismatch. It lists each one in the pane, with the facts, so you can decide. The fetch must succeed for these checks to run.

MismatchExampleShown as
Flag status disagrees with AzureFlag doing, but Azure says To DoExpected Azure state for doing is Doing
Expected states by flagclaiming → To Do or Doing; doing → Doing; finishing → Doing or Done; done → DoneThe table the check uses
Item past To Do with no flagAzure says Doing, but no flag exists for itOnly To Do items may lack a flag
Flag for an item no longer fetchedItem deleted, moved to another project, or unassignedThe flag is listed with its last known state
Unreadable flag or state fileInvalid JSONThe file path and the parse error
Top item already flaggedSection 8, step 7A conflict, not a mismatch

Each row in the pane has a stable key built from its kind and item id. A mismatch is reported once, and raised again only if it changes.

10. Actions

These are Herdr plugin actions added to herdr-plugin.toml. Action ids have no dots, as Herdr requires. Each one reads active-project.json for the repo root and never trusts the focused workspace.

Every invocation follows the same pattern, tested on list-my-work-items:

  1. The mod invokes the action. The call returns at once with a log_id and status running.
  2. On later ticks, the mod reads herdr plugin log list --plugin dev.automation and finds that log_id.
  3. Once the status is no longer running, exit_code 0 means success. The stdout and stderr are the output the mod reports.

dev-fetch-work-items

  • Input: none.
  • Does: runs the WIQL query used by list-my-work-items, limited to the project and to To Do, Doing and Done. Writes work-items.json with a new fetchedAt.
  • Outcome: the plugin log's exit code and stdout. Its stdout also includes the HERDR_PLUGIN_STATE_DIR it ran with, which start compares with the default path.
  • Idempotent: yes. Writes only the fetch file.

dev-claim-work-item

  • Input: requests/claim.json, { "workItemId": N }. Deleted after reading.
  • Does, in order:
    1. Check that the item is still To Do in Azure. If not, archive the claiming flag with the reason.
    2. Set the Azure state to Doing.
    3. Create the worktree and branch from a fresh origin/<base>. If the worktree already exists (a resumed attempt), keep it.
    4. Move the flag to doing, with the branch and worktree paths.
  • On failure: if Azure was already set to Doing, set it back to To Do. Archive the claiming flag with the reason. The mod reports it.
  • Idempotent: yes, for a resumed attempt.

dev-finish-work-item

  • Input: requests/finish.json. Deleted after reading.
  • Refuses unless the result file exists with "status": "success".
  • Does, in order:
    1. Refuse if the worktree has uncommitted changes. Report them. Do not commit on the agent's behalf.
    2. Push the branch to origin. Never a force push. Never a push to the base branch.
    3. Find an open pull request for the branch into the base branch. If none, create one with gh pr create, title and body taken from the work item.
    4. Set the Azure state to Done.
    5. Move the flag to done, with the pull request URL.
  • Idempotent: yes. Each step checks before it acts.
  • On failure: the flag stays finishing. The mod retries on the next tick, and reports after the retry fails.

dev-reset-work-item

  • Input: requests/reset.json, with the work item id and the reason.
  • Does: archives the flag with the reason, sets Azure back to To Do, and keeps the worktree and branch.
  • Refuses an item whose flag is finishing or done.
  • Note: the mod closes the pane and writes the attempt count. The action does not touch panes.
Invoking an action does not wait for it. The call returns at once. The mod waits by checking the plugin log on later ticks, and the run's exit code and stdout are its outcome. The state files still hold the flags and the queue, which is what the mod reads to decide the next step.

11. Agent launch and completion

Launch

  1. Split a pane. herdr pane split --current --direction right --cwd <worktree> --no-focus. The new pane id is taken from the response.
  2. Trust the worktree. Before starting the agent, set hasTrustDialogAccepted to true for the worktree's path in ~/.claude.json. Refuse if the path is not under the configured worktree folder. Without this, Claude stops at its "trust this folder" prompt, and the agent never becomes ready. Tested in spike 5.
  3. Start may report "not ready" at first. In spike 5 the start call returned agent_not_ready, yet the agent was idle about 15 seconds later. The mod treats that error as "still starting": it does not fail the item, and it checks the agent again on later ticks.
  4. Start the agent. herdr agent start wi-<id> --kind claude --pane <pane-id> -- --dangerously-skip-permissions. The name must match Herdr's rule ([a-z][a-z0-9_-]{0,31}), which wi-<id> does.
  5. Send the prompt. herdr agent prompt wi-<id> "<prompt>", without --wait. The mod polls on later ticks.
  6. Record the agent. Write agents/wi-<id>.json.

The prompt

The prompt is built from the work item and includes these parts:

  • The work item id, title, type, and description, pasted as plain text.
  • The worktree path and branch. The agent works only inside them.
  • The instruction to implement the item, run the project's tests, and commit with a message that names the item id.
  • The instruction not to push and not to open a pull request.
  • The result file path and exact format: results/wi-<id>.json, with status set to success or failed, a summary, and the commit id. Written last, after the commit.
  • For a resumed attempt: the note that a previous attempt ended without a result, so the agent should inspect the existing commits and continue.
The prompt is the agent's only instructions. The work item's description is untrusted text written by someone else. It is sent as data inside the prompt, but the agent can still act on what it says. The bypassed permissions make that a real risk (section 14).

Completion

An agent is complete when all of these hold on a tick: the agent is idle or done, and the result file exists and is valid JSON. If the result says success, the finish action runs. If it says failed, the mod reports it and waits for you.

The mod never waits in a blocking call. A tick reads the state, acts on it if it has changed, and returns.

Reading output

For troubleshooting, herdr agent read wi-<id> --source recent-unwrapped --lines 120 shows what the agent last printed. The mod does not use it to decide anything.

12. Notifications

Notifications use two surfaces, as you chose.

  • Pane. A ui.render pane, opened by /herdr-dev status or whenever a new conflict or mismatch appears. It lists every open item with its kind, item id, the facts, and the time it was first seen. It stays open until you close it.
  • Toast. A short toast when a new conflict or mismatch is raised, and when an item reaches Done. A toast never repeats for an item it has already shown, so the same mismatch does not toast on every tick.

Each row has a key built from its kind and item id, so the pane updates in place instead of stacking duplicates. A row leaves the pane when its cause is gone, for example when you fix the Azure state.

14. Safety

The agent runs with bypassed permissions. It can run any command, edit any file it can reach, and install software, all without asking you. The worktree is a directory boundary, not a sandbox: the agent can still reach files outside it and can still use the network. Treat the agent as trusted code you have not reviewed.
  • Blast radius. The agent can delete files in its worktree, or anywhere the user account can write. Keep the loop running only on repositories and machines where that is acceptable.
  • Outward effects. Pushes, pull requests and Azure state changes happen only in the four actions, never in the agent. The agent is told not to push or open pull requests, and the finish action checks the result before it does either.
  • Trusted folders. Trusting a worktree lets Claude run the code in it without asking. The mod trusts only the worktrees it creates for work items, never a folder you chose, so the trust step cannot widen what the agent can reach.
  • Never to main. Pushes go only to the feature branch. Pull requests target the base branch. The finish action never pushes to the base branch and never force-pushes.
  • Merging stays with you. The mod never merges a pull request.
  • Azure writes. Only the state field changes. No other fields, no comments, no deletions.
  • Secrets. .env is read but never printed, copied, sent in a prompt, or written to a state file. The mod passes no Azure credentials to the agent. The agent runs as your user account, which can already reach them.
  • Prompt injection. A work item's text reaches the agent. The agent acts only in its worktree, and its output reaches Azure and GitHub only through the finish action, which you can review in its pull request.
  • Stopping. /herdr-dev stop stops the loop only. To stop an agent, close its pane or run herdr agent send-keys wi-<id> ctrl+c.
Why bypassed permissions, and what you could choose instead

Without bypass, the agent stops and waits for approval in its pane, so the loop stalls whenever you are away. The alternatives are an auto permission mode, which a classifier approves, and default mode, which waits for you. Both reduce unattended progress. Bypass is your decision, recorded here so you can revisit it.

Facts the design relies on, with their sources
  • herdr plugin action invoke takes no arguments, and returns at once with the run's log_id and status running. Measured on this machine.
  • herdr plugin log list --plugin dev.automation records each run's status, exit_code, stdout, stderr, and start and finish times. Measured on this machine.
  • The invoke context includes the workspace, tab and focused pane, and the working directory. Measured on this machine. The focused pane can change while the loop runs, so the design does not use it.
  • A new folder opens with Claude's "Yes, I trust this folder" prompt. The prompt blocks the agent until someone answers it. Measured on this machine with a test agent. The trust entry is stored as hasTrustDialogAccepted in ~/.claude.json, which I read on this machine (key names only).
  • Startup hooks are one-shot. Herdr plugins documentation, herdr.dev/tui/docs/plugins/.
  • HERDR_PLUGIN_STATE_DIR is for local runtime state. Its path is not documented.
  • The state directory at ~/.local/state/herdr/plugins/dev.automation exists on this machine, and the Herdr binary references XDG_STATE_HOME.
  • Agent states idle, working, blocked, done and unknown, and the JSON errors timeout, agent_blocked, agent_prompt_stalled and agent_not_ready. The /herdr skill.
  • dev.automation is installed from the GitHub checkout, so new actions reach Herdr only after a push and an update.

16. Phases and tests

Phases, after you approve this document

  1. Spikes. Answer open spikes 2 and 3 in section 15. Spike 1 is not needed, and spike 4 is answered.
  2. Actions. Add the four actions and their scripts. Reuse the query and update code in list-my-work-items.ts and create-work-item.ts, and the repo-root and .env code in configure-azure-defaults.ts.
  3. State and judgement, without outward effects. The mod's guards, flags, mismatch reports and pane, tested with the actions stubbed.
  4. Agent launch and completion. Pane split, agent start, prompt, result file, the hanging rule and the retry cap.
  5. Finish. Push, pull request and Done, with idempotent retries.
  6. Commands and notifications. start, stop, status, the pane and the toasts.
  7. Rollout. You push the branch to GitHub and update the Herdr plugin yourself.

Tests

  • Static: claude plugin validate on the mod, and type-checking with tsc.
  • Mod tests: claude plugin test with $.process.run and $.fs mocked. Cover every guard, every hanging condition, the retry cap, each mismatch row, the pane's keys, and the one-at-a-time rule.
  • Action dry runs: each action with a --dry-run flag that prints the Azure, git and gh commands it would run, against the real board.
  • End to end: one run on a throwaway repository and a disposable work item, with the pull request closed afterwards. No real pull request against your project until the end-to-end run passes.
